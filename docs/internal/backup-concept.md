# Concept: Backup & Restore

Redesigned 2026-08-19 (see `notes/2026-08-19-backup-versioning-grill.md` for the full discovery session). Replaces the previous version of this document.

## Starting point

The existing `/system/backup` route ([system-route.ts:100](../../js_automations/routes/system-route.ts#L100)) already zips everything under `SCRIPTS_DIR` (scripts, `.storage/settings.json`, `data/`, `libraries/`) except `node_modules`/`.git`. There is no restore endpoint at all today. This redesign keeps the same scope and adds restore, scheduling, off-box storage, and safety.

## Scope

**In the backup:** `scripts/*.ts`, `libraries/`, `.storage/settings.json`, `data/` — unchanged from today.

**Deliberately NOT in the backup:**

- Installed card packs (`HA_CONFIG_DIR/www/jsa-cards`) and Lovelace resource registrations. These are derived build artifacts generated by `card-manager.ts` from scripts with a `@card` header ([card-manager.ts:429](../../js_automations/core/card-manager.ts#L429)). A restore triggers the existing `reconcile()` pass afterward to regenerate them from the restored scripts — no need to back them up separately.
- Supervisor add-on options (port, log_level, etc., set via the HA UI). Owned by HA Supervisor's own full-backup/snapshot system — a separate, non-overlapping responsibility.

## Creation

Two trigger paths, both producing the same zip format:

1. **Manual** — the existing click/download stays, for "back this up right now before I change X."
2. **Automatic** — a scheduled job (cron-style, configurable in Settings) writes a backup to disk on the server, no download involved. Separate mechanism from the per-script `ha.cron()` scheduling used by user scripts ([worker-wrapper.ts](../../js_automations/core/worker-wrapper.ts)) — this is a simple server-level interval/cron job.

## Storage & retention

- **Local (always):** written to a dedicated folder outside `SCRIPTS_DIR`, e.g. `/config/js-automations-backups/`, so a restore can never overwrite the backup history it might need to fall back on.
- **WebDAV (optional):** a WebDAV target (URL/user/password) configurable in Settings. When set, every backup — manual or automatic — is additionally uploaded there, best-effort. The local copy stays authoritative if the upload fails.
- **Retention:** by count, default 14, same rule applied to both the local folder and the WebDAV target. Configurable in Settings.

## Restore — a rare, disaster-recovery tool

Restore is scoped deliberately narrow: for total loss or a server rebuild, not for day-to-day "I broke one script" recovery. That daily case is handled by script version history instead (see `github-integration-concept.md`) — restoring a single file from a zip diff is a fallback, not the primary UX.

### Flow

1. User uploads a backup zip.
2. Server unpacks it to a temp location and diffs it against the current `SCRIPTS_DIR` state.
3. UI shows the diff as a checklist — changed / added / deleted files, each individually selectable — so a user can restore a subset instead of everything.
4. User confirms via a normal summary dialog ("N changes will be applied, the server restarts briefly, a snapshot of the current state is taken automatically first"). No type-to-confirm friction — the safety nets below already remove the "blind destructive" risk.
5. **Pre-restore snapshot:** before touching anything, the current `SCRIPTS_DIR` state is written to `pre-restore-<timestamp>.zip`. This is the safety net — if the restore turns out wrong, that snapshot is itself just restored back. Kept in its own small reserve (e.g. last 5), separate from the normal rotation, so a restore mistake can't be rotated away by an unrelated scheduled backup.
6. **Stop** the kernel/workers (`workerManager.shutdown()` or equivalent) before any file is overwritten, avoiding a script loading a half-written file or a worker running against an inconsistent state.
7. Apply only the checked subset of changes from the zip.
8. Reload settings.
9. Trigger the card-manager `reconcile()` pass to rebuild cards/Lovelace resources from the restored scripts.
10. Restart the kernel/workers.
11. UI shows success, with a link back to the pre-restore snapshot for an immediate undo.
