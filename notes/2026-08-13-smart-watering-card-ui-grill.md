# Smart Watering Card UI: Grill / Discovery Notes
Date: 2026-08-13 · Goal: redesign the `smart_watering.ts` `@card` (scripts/smart_watering.ts, decoded from its base64 `__JSA_CARD__` block) — collapsed-header status icon/text, an icon-only Automatik/Stopp affordance visible even collapsed, dropping the expanded Status tab in favor of zone-only tabs (+ optional Config tab), and fixing the duration stepper's 5-min increment losing round numbers.

## Summary / key decisions

**Collapsed header (`.status-strip`) redesign:**
1. **Height cap is collapsed-only** — must not grow a pixel (drives the Lovelace grid tile size). Expanded height is free to change.
2. **Zone-number badge on the status icon** — a small numbered dot overlaid on the 40×40 status icon, showing which zone is currently active (pre-watering/soaking/watering/manual-on). Solves the real ambiguity (which zone), independent of text truncation. Icon *shapes* stay as they are — the 5-way shared-droplet icon (`paused`/`pre_watering`/`soaking`/`watering`/`manual_on` all use the same SVG path) is intentionally left alone; not worth a 4th icon set.
3. **Icon-only Automatik/Stopp buttons move into the strip itself**, visible collapsed AND expanded, replacing the old text-only `.quick-actions` row (which is removed entirely — one control, not two). Placed right side, directly before the chevron. The `.pulse` dot is dropped to make room (redundant with the tone-colored icon background anyway).
4. **Label (bold line) shrinks to a single status word** per state (Bereit/Vorbewässerung/Ruhephase/Bewässerung/Manuell an/Regen erwartet/Fehler/Pausiert) — zone comes from the badge (#2), timing from the sub-line (#5). Source is `STATUS_LABEL` in `scripts/smart_watering.ts:120-129`; the `(${zone.name})` suffix appended at `:159` should be dropped too, since the badge now covers that.
5. **Sub-line format tightens to e.g. "Fr, 5:08h"** — no "Start" prefix, no comma after the weekday, no leading zero on the hour, "Uhr" → trailing "h". User-volunteered, mid-turn.

**Expanded view restructure:**
6. **Status tab is dropped entirely** — tabs become zone-only. The "N of M zones active" summary line disappears (already implicit via `.is-off`-styled tabs for disabled zones). **No Config tab yet** — deferred until an actual global (non-per-zone) setting exists to put in it, e.g. a future rain-sensitivity selector.

**Duration stepper bug fix:**
7. **Round-to-nearest-multiple-of-step on click**, both directions, applied to the stepper click handler in `_wireEvents` — durably fixes any stored value that isn't already a multiple of the current step (not just today's `durationWatering: 51` vs. `step=5`), applied uniformly to both steppers.

**Not yet nailed down (deliberately deferred to implementation time, not blocking):** exact German wording per status label (Q4's list is a proposal), exact badge visual treatment (size/position/color on the icon), and the structural HTML fix for nesting action buttons inside what's currently a single `<button id="expandToggle">` wrapping the whole strip.

## Reference: current implementation (read directly from code, not asked)
- Card source lives as a single base64-encoded line (`scripts/smart_watering.ts:582`, the `__JSA_CARD__` block), decoded to `card_decoded.js` in scratchpad for this session.
- **Collapsed header** (`.status-strip`, always visible): 40×40 tone-colored icon (per-status SVG path, `STATUS_ICON`/`STATUS_TONE` maps) + `status-text` (bold `label` = `attrs.status_text`, single line, `white-space:nowrap` + ellipsis; `sub` = small muted line built from `_fmtRemaining`/`_fmtWhen`) + a `.pulse` dot (only shown when `tone === 'good'`, purely decorative — no number, doesn't encode which zone) + chevron. Padding `16px 18px`, `gap:14px`.
- **Expanded area** (`.expand-area`, only when `_expanded`): `.quick-actions` row with two full-text buttons ("⚡ Automatik", "■ Stopp"), then `.tabs` (`Status` tab + one tab per zone, zone tabs get `.is-off` styling when `zone.enabled === false`), then one `.panel` per tab. Status panel = just a one-line callout ("N von M Zonen aktiv..."). Zone panel = zone-active toggle, Pflanzentyp select, Dumb/Smart segmented control, active-weekdays row of day circles, two duration steppers (Vorbewässerung `step=1 min=0`, Bewässerung `step=5 min=1`), a manual valve toggle, "Jetzt bewässern" button.
- `getCardSize()` returns `2` collapsed / `8` expanded (HA grid row units) — the actual height constraint lever if the expanded layout changes.
- `_fmtWhen()` today: `d.toLocaleString('de-DE', { weekday: 'short', hour: '2-digit', minute: '2-digit' })` → renders as "Fr., 05:08" (note the literal dot after weekday from `toLocaleString`), wrapped as `Start <b>${whenArmed}</b> Uhr` in the sub line.
- Stepper click handler (`_wireEvents`): `next = Math.max(min, zone[field] + dir * step)` — a flat `±step` from the *current* value, no snap-to-multiple. Since `durationWatering`'s current stored value (51) predates today's `step="5"` (it was likely `step="1"` before), 51 ± 5 never lands on a round number (56, 46, 41, 36...) — the stepper doesn't round, it just offsets from whatever's already stored.

## Q&A log

### Q1 — What does "höher als so sollte es nicht werden" actually bound?
- Asked: Does the height cap apply to the **expanded** card (2nd screenshot, `getCardSize()` returning `8`) — i.e. whatever we do with tabs/Config, the expanded card must not exceed today's height — or does it also constrain the **collapsed** strip (1st screenshot) from growing even slightly to fit a badge/icon buttons?
- Captured: **Only the collapsed strip.** The 1st-screenshot header height (`.status-strip`, currently `padding: 16px 18px` around a 40×40 icon) is the hard ceiling — it must not grow, since that's what counts toward the Lovelace grid tile size (`getCardSize()` returns `2` collapsed). The expanded height (`getCardSize()` returns `8`) is free to change — dropping the Status tab will likely shrink it anyway, and small growth there isn't a concern since the user is already focused/scrolled in when expanded.
- Flags: none — this directly gates Q2/Q3 (badge + icon buttons must fit in the existing collapsed strip footprint, not add height to it).

### Q2 — What should the badge number on the status icon encode?
- Asked: (with a code finding surfaced first — `STATUS_ICON` renders the *identical* droplet path for 5 of 8 statuses: `paused`, `pre_watering`, `soaking`, `watering`, `manual_on`; only `armed`/`canceled_rain`/`error` look different, which likely explains why "was gerade gemeint ist" isn't visible from the icon alone) Should the dot+number show the **active zone number**, the **phase number** (1=pre-watering/2=soak/3=watering), or a **count of active/queued zones**?
- Captured: **Active zone number.** Solves the actual ambiguity — which zone is meant — independent of how much the label text gets truncated. E.g. a small numbered badge overlaid on the status icon showing "2" when zone 2 is the one currently pre-watering/soaking/watering/manually on.
- Flags: whether the 5-way identical-droplet-icon problem also needs a real fix (distinct icons per phase) is still open — the zone-badge doesn't by itself disambiguate *phase*, only *zone*. Follow-up question pending.

### Q2b — Distinct icons per phase, or keep the shared droplet?
- Asked: Should `pre_watering`/`soaking`/`watering`/`manual_on` each get their own icon shape, or stay the shared droplet since the zone-badge (Q2) already solves the main ambiguity?
- Captured: **Keep the shared droplet for all of them.** Phase detail is already available via the sub-text ("noch X min"); a 4th icon set would be extra design/implementation work without clear added value. Only the zone-number badge is being added — icon shapes stay as-is.
- Flags: none — decided, closes this sub-branch.

### Q3 — Do icon-only Automatik/Stopp buttons replace or add to the existing text buttons?
- Asked: Today's "⚡ Automatik"/"■ Stopp" text buttons only exist in `.quick-actions`, which is only visible when expanded. Should icon-only versions move into `.status-strip` (visible collapsed AND expanded) and fully replace `.quick-actions`, or coexist alongside it (icon buttons collapsed, text buttons still shown when expanded)?
- Captured: **Replace — single always-visible control.** Icon-only Automatik/Stopp buttons move into `.status-strip` (visible in both collapsed and expanded states), and the current `.quick-actions` text-button row is removed entirely. Avoids two controls for the same action, and removing `.quick-actions` also helps shrink the expanded height (aligns with Q1's freedom to reduce expanded height).
- Flags: exact placement within the strip (left/right of the icon, before/after the chevron) and click-target mechanics (the whole strip is currently one `<button id="expandToggle">` — nesting action buttons inside needs `stopPropagation()` so pressing Automatik/Stopp doesn't also toggle expand) — not yet asked, follow-up pending.

### Q3b — Icon-button placement and the pulse dot
- Asked: (with ASCII layout previews) Where do the icon-only Automatik/Stopp buttons sit in the strip, and does the existing `.pulse` dot (animated, shown only when `tone === 'good'`) stay?
- Captured: **Right side, directly before the chevron; `.pulse` dot is removed entirely.** The pulse was redundant with the tone-colored icon background anyway, and dropping it frees exactly the horizontal space needed for the two icon buttons without widening/heightening the row.
- Flags: still open — the `<button id="expandToggle">`-wraps-everything structural issue (buttons-in-a-button is invalid HTML) needs an actual markup fix: the strip likely needs to become a non-button container (e.g. a `div` with a click handler on itself minus the action buttons, or the action buttons + chevron pulled outside the `<button>` with `stopPropagation()` on their own click handlers). This is an implementation detail for build time, not something requiring another question.

### Q3c — Sub-line date/time format (user-initiated, mid-turn)
- Asked: (not asked by me — user volunteered this while I was reading the card source) Reacting to the current `sub` line format "Start **Fr., 05:08** Uhr" (built by `_fmtWhen()`'s `toLocaleString('de-DE', {weekday:'short', hour:'2-digit', minute:'2-digit'})`, which produces "Fr., 05:08" with a literal comma+dot and zero-padded hour).
- Captured: **Full "Datum" framing isn't needed** — user's exact example: "Fr, 5:08h" would already be enough when space is tight. Reading this together with the current code: drop the comma after the weekday abbreviation, drop the leading zero on the hour, drop the "Uhr" suffix in favor of a trailing "h", and likely drop the "Start" prefix word too (implied by "wenn uns der Platz fehlt" — this is explicitly the fallback for when space is short, which after Q1–Q3b's icon-button changes it will be). Exact final wording (keep "Start" or not) not 100% pinned — reasonable default: just "Fr, 5:08h" alone, no "Start" prefix, matching the user's own example verbatim.
- Flags: none blocking — treat "Fr, 5:08h" (no "Start", no "Uhr", no comma, no leading zero) as the target sub-line format for the `armed` state. Still need the format for the *other* states' sub-lines (remaining-time countdown, active-zone name) — see Q4 below.

### Q4 — How short should the bold label text get, per status?
- Asked: (with an ASCII preview) Today's label reads e.g. "Automatik aktiv – wartet auf..." and gets truncated. With the zone badge (Q2) and a tighter sub-line (Q3c) covering zone + timing, should the label collapse to a single status word, or stay a short phrase (just shorter than today)?
- Captured: **Single-word status labels.** E.g. "Bereit" (armed), "Vorbewässerung", "Ruhephase" (soaking), "Bewässerung" (watering), "Manuell an" (manual_on), "Regen erwartet" (canceled_rain), "Fehler" (error), "Pausiert" (paused). The label now only answers "what's happening" — zone comes from the badge, timing from the sub-line. Exact German wording per status listed here is my proposed set, not yet individually confirmed word-by-word — reasonable to finalize at implementation time rather than one-by-one here.
- Flags: resolved by direct code lookup (not asked) — `STATUS_LABEL` (`scripts/smart_watering.ts:120-129`) is the actual source: `paused: 'Pausiert'`, `armed: 'Automatik aktiv – wartet auf Start'`, `pre_watering: 'Vorbewässerung läuft'`, `soaking: 'Einweichen'`, `watering: 'Bewässerung läuft'`, `manual_on: 'Ventil manuell geöffnet'`, `canceled_rain: 'Abgebrochen (Regen erwartet)'`, `error: 'Fehler'` — two call sites publish it (`:159` and `:471`). **Found a compounding cause of the truncation**: `:159` appends `` (${zone.name})`` to the label whenever a zone is involved — i.e. today's label is already trying to cram the zone name in as text (e.g. "Bewässerung läuft (Zone 1)"), which is exactly what made it overflow in the first place. Once the zone badge (Q2) ships, this `(${zone.name})` suffix becomes redundant and should be dropped, not just shortened — both the map values AND the `:159` concatenation need editing at implementation time.

### Q5 — What happens to the Status tab's content, and is a Config tab needed now?
- Asked: (with option previews) Today's Status tab holds just one line ("N von M Zonen aktiv..."). If the tab is dropped, does that line move somewhere else (e.g. a strip above the tab bar), or disappear entirely? And is a Config tab worth adding now, or only once there's an actual global setting to put in it?
- Captured: **Callout is dropped entirely, no Config tab yet.** The "N of M zones active" info is already implicit in the zone tabs themselves (a `.is-off`-styled tab already visually marks a disabled zone) — no separate summary line needed. Tabs become just one per zone, nothing else. A Config tab is deferred until there's an actual global setting to put in it (e.g. the future rain-sensitivity selector from [[project_beregnung_multizone_roadmap]] once it's ported to smart_watering.ts) — no point building an empty placeholder tab now.
- Flags: none — decided. Note for later: when rain-sensitivity (or any other global, non-per-zone setting) actually gets added to `smart_watering.ts`, that's the trigger to introduce a Config tab, not before.

### Q6 — Fix for the 5-min stepper losing round numbers
- Asked: (with an ASCII example) `durationWatering`'s stepper has `step="5"` but the stored value (51) predates that (was likely `step="1"`). The click handler does a flat `zone[field] + dir*step` with no rounding, so 51 can never return to a multiple of 5. Three options offered: round-to-nearest-multiple-of-5 on the *first* click in each direction (then normal ±5 stepping), revert step back to 1, or make the number tappable/editable for exact entry.
- Captured: **Round to nearest multiple of 5 on click, both directions.** E.g. from 51: minus → 50 (not 46), plus → 55 (not 56); from 50 onward, normal ±5 stepping applies. This is a general, durable fix (not a one-time correction) — solves the same problem for any stored value that isn't already a multiple of the current step, not just today's specific 51.
- Flags: implementation detail for later — exact rounding function, likely something like `dir > 0 ? Math.ceil((current+1)/step)*step : Math.floor((current-1)/step)*step`, clamped to `min`. Applies to `_wireEvents`'s `.stepper[data-zone-field]` handler in the card; should probably apply to *both* steppers (Vorbewässerung `step=1` too, though step=1 never has this problem since every integer is a "multiple of 1" — effectively a no-op there, safe to apply uniformly).
