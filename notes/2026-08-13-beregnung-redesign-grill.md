# Beregnung Redesign: Grill / Discovery Notes

Date: 2026-08-13 · Goal: fix perceived "shuts off after run" behavior, add real on/off without timer, expose watering duration as a config number field, and surface any other improvements to scripts/beregnung.ts

## Summary / key decisions

1. **Bug (not UX):** After an automatic or manual cycle, Beregnung's buttons go `unavailable` and the script shows as "off" in the addon — only Beregnung is affected, nothing else in the addon. No error was logged either time it was observed (no crash message, no unhandled rejection). Root cause unidentified from static code reading (`ha.action()` registration should keep the worker ref-counted alive; the script-watcher only watches the source dir, not the persistent-store data dir — both plausible causes ruled out). **Plan: reproduce live in DEV** (see #4) to catch it with the log panel open.
2. **Real on/off switch:** Add a new `switch` entity that opens the valve and holds it open until manually turned off again — no timer, no pre-watering/soaking phases, no `next_change`. Coexists with the existing `button.beregnung_wasser_start` (timed manual watering stays as-is). Toggling the new switch during an active automatic cycle cancels that cycle and hands control to manual mode (same pattern `startManualWatering()` already uses).
3. **Watering duration as config entity:** Add one real `number` HA entity for `durationWatering` (currently a hardcoded `CONFIG` constant, 50 min) — the entity itself is the source of truth, script reads its current value at the moment a new cycle starts. Pre-watering and soaking durations stay fixed `CONFIG` constants, not exposed. An already-running cycle keeps the duration it started with.
4. **DEV repro plan (user-initiated):** Build a DEV variant of the script with the actual `ha.entity(...).turn_on()/turn_off()` valve-switching calls commented out, and all three phase durations shortened to a few seconds, so automatic/manual cycles can be exercised repeatedly and fast, with the JSA log panel open, to catch the silent "off" bug.
5. **Scope for this pass:** Only items #1–#3 above. Existing deferred TODOs (physical HmIP button wiring, dry-run switch for prod testing, rain forecast, leak detection, multi-zone) are explicitly OUT of scope — stay as-is.

- Checked the Supervisor/container log (3rd log source) for 08:40–08:42: only unrelated old entries (Zigbee2MQTT option warnings, a resolution/system-check cycle at 08:27:45) — **nothing** about the `js_automations` addon crashing, restarting, or being OOM-killed. This rules out a Supervisor/Docker-level restart.

### ROOT CAUSE FOUND — a silent log-level drop was hiding the answer the whole time

- Read `js_automations/core/worker-manager.ts:1301-1358` (the `worker.on('exit', code)` handler) and `js_automations/core/kernel.ts:622-657` (`_onScriptExit`): every worker exit is classified as `type: 'success'` (clean, `code === 0`) or `type: 'error'` (`code !== 0`), and **either way** gets logged via `this.logManager.add(level, 'System', \`${filename} ${reason}\`)`—`level`is`'debug'`for a clean/success exit,`d.type`(i.e.`'error'`) for a crash.
- Read `js_automations/core/log-manager.ts:88-94` (`LogManager.add()`): messages from source `'System'` are filtered against a **global** `systemLogLevel` setting (`Settings → System → Log Level`, default **`'info'`**) — `if (LOG_LEVELS[lvl] > LOG_LEVELS[systemLogLevel]) return null;`. Since `debug` (3) > `info` (2), **a clean/success exit's log line is silently discarded before it's ever written to `logs.json` — not hidden by a UI filter, never persisted at all.** This is a fundamentally different, stronger dead-end than the wrong-log-panel or lost-history explanations already ruled out.
- User confirmed the JSA log panel had been **freshly cleared right before the test**, and after the whole incident it contains only the 3 lines already known (UniFi start + 2× Beregnung start) — **zero** `System`-sourced exit/crash line for `beregnung.ts` anywhere in that window. This is exactly consistent with a `type: 'success'` (clean, `code === 0`) exit — if it had been `type: 'error'` (a crash), that would log at `'error'` level, which is NOT filtered by the default `'info'` threshold and would have survived. So: **the worker exited cleanly (`process.exit(0)`), not via a crash** — narrowing things much further than "silent restart" alone.
- A clean `code === 0` exit happens when: `ha.stop()`/`ha.restart()` is called from the script (not present in beregnung.ts), a graceful `stop_request` from the manager completes, `SIGTERM` fires, or — the original, longest-standing hypothesis from earlier this session — **the worker's own keep-alive ref count (`_refCount`) drops to 0 while idle**, letting Node's event loop drain naturally with exit code 0. That was earlier deprioritized on the reasoning that the 3 `ha.action()` registrations should hold permanent refs — worth re-examining now that the new `switch.beregnung_ventil` adds an `ha.on()` subscription too, and now that we have a concrete, narrowed failure mode to test against instead of a vague "something kills it."
- Also: per `kernel.ts:622-657`, a clean exit with `reason: 'finished'` (not in the `transientReasons` allowlist) should mark the script as **permanently stopped** (`stateManager.saveScriptStopped()`) — not auto-restarted by that code path. Yet the script clearly came back up 77s later (`08:41:37`). **What actually triggered the restart is still unidentified** — not the `type: 'error'` auto-recovery path (ruled out above), so something else (UI action, `script_command_router.ts`'s MQTT-driven start/stop, or another path not yet traced) must have called `startScript()` again. Not yet investigated in this session.
- **Concrete, high-value next step:** set `Settings → System → Log Level` to **`Debug`** in the production addon (temporarily) so that next time this happens, the `System`-sourced `"beregnung.ts finished"` / `"beregnung.ts crashed (Code N)"` line actually gets written to `logs.json` instead of being silently dropped — this alone will likely resolve the remaining "clean exit vs crash" and "what restarted it" questions definitively. -> user to flip this setting and reproduce again.

### ROOT CAUSE CONFIRMED AND FIXED

- With `Settings → System → Log Level` set to `Debug` in production, the user reproduced it again and captured the full log: `09:32:30` "Timer starten" pressed (Dauer=1) → cycle ran correctly for 60s → `09:33:30` cycle completed normally (valve OFF, status `paused`) → `09:33:40`, exactly 10s later, **`[System] beregnung.ts finished`** — a clean exit (`process.exit(0)`, not a crash).
- Root cause, found by reading `worker-wrapper.ts` directly: the worker keeps itself alive via a manual ref-count (`_addRef()`/`_releaseRef()` wrapping `parentPort.ref()/unref()`). `ha.action()` and `ha.on()` each add one **permanent** ref (3 buttons + 1 switch-subscription = 4 for this script). Every `ha.entity(id).service()` call (e.g. `turn_on()`/`turn_off()`) does one `_addRef()` — but on completion it was released **twice**: once inside `ha.entity()`'s own resolve/reject closure, and again unconditionally in the shared `SIMPLE_RESPONSE_TYPES` message handler that 7 other APIs (installCard, cacheAsset, history.get/statistics, renderTemplate, getCalendarEvents, getTodoItems) also share — but those 7 only release once, so only `ha.entity()` double-released. This bug was introduced when 8 near-identical response handlers were consolidated into one shared handler (per a comment already in the code) and the entity-specific double-release wasn't caught.
- Net effect: every `ha.entity()` call costs the worker 1 permanent ref instead of being neutral. `setValve()` (used by `cancelCurrentCycle()`, and both ends of every watering cycle) calls it 3× per manual/automatic cycle, plus 1× on the restart-recovery path — so after exactly 4 such calls (which is _exactly_ what happened: 1 at boot's recovery + 2 at cycle start + 1 at cycle end), the permanent-ref budget of 4 hits zero and the idle worker's event loop drains naturally with exit code 0. Matches every observed symptom: no crash log (it's not a crash), only affects scripts that call `ha.entity()` repeatedly with few permanent refs (only `beregnung.ts` and `keller_klima.ts` use `ha.entity()` in this codebase — `keller_klima.ts` runs its `evaluate()` loop with several `ha.entity()` calls every 5 minutes via `setInterval`, and is likely _even more_ exposed), happens after both automatic and manual use (both consume the same shared budget), and is completely silent by default because a clean exit only logs at `debug` level, which the default `system_log_level: 'info'` silently drops before it's ever written to `logs.json`.
- **Fix applied** in `js_automations/core/worker-wrapper.ts` (the `ha.entity()` proxy's service-call implementation): removed the redundant `_releaseRef()` from the stored `resolve`/`reject` closures (now plain `resolve(apiProxy)`/`reject`), and added the release explicitly to the timeout-fallback branch instead (the one path that doesn't go through the shared response handler). Now every `ha.entity()` call releases its ref exactly once, matching the other 7 `SIMPLE_RESPONSE_TYPES` APIs. This is a platform fix — benefits every script using `ha.entity()`, not just Beregnung.
- **Verified in DEV**: rebuilt backend (`npm run build:backend`, clean typecheck), restarted the dev server, pressed "Timer starten" 3× back-to-back (1-min cycles = 9 `ha.entity()` calls total, more than double the old 4-call failure threshold) — all entities (`sensor.beregnung_status`, the 3 buttons, `switch.beregnung_ventil`, `number.beregnung_dauer`) stayed available and correct throughout and well after. Bug does not reproduce post-fix.
- **Not yet deployed to production** — this is a core-code change (`worker-wrapper.ts`), not a script edit, so it only reaches the user's real HA instance via a proper addon release (per [[feedback_release_process]] — always `npm run ship:patch/minor/major`, never a manual version bump).
- Bonus fix applied alongside: `number.beregnung_dauer` now echoes its confirmed value back via `ha.update()` after a `set_value` command — MQTT number entities without `optimistic: true` don't reflect a command in their displayed HA state until the device (script) publishes it back; without this, the number field's _display_ could look like it "reverted" even without the ref-count bug being involved at all (the internal cached value was always correct either way). Same pattern as the existing `switch.beregnung_ventil` echo-back.
